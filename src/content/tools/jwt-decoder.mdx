## What it does

Paste a JSON Web Token and see its decoded header and payload as formatted JSON, with the standard claims explained: `exp`, `iat`, and `nbf` are shown as readable UTC timestamps with relative time, and a status line tells you whether the token is currently valid, not yet valid, or expired. The signature is displayed raw and explicitly **not verified** — this is an inspection tool, not a validator.

## Examples

**"Why is this request getting 401s?"** Paste the bearer token from the failing request. If the status line reads `EXPIRED 2 hours ago`, you've found the bug — likely a token cached past its lifetime or a refresh flow that isn't firing.

**Checking what your identity provider actually puts in the token.** Decode a token issued by your auth server and look at the payload: is the `aud` claim what your API expects? Did the custom `roles` claim make it in? Misconfigured claim mappings are visible in seconds.

**Clock-skew hunting.** A token that fails "before" it should may have an `nbf` a few seconds in the future relative to the consuming server. The claims table shows `nbf` against your local clock, which makes skew between issuer and consumer easy to reason about.

## Edge cases & notes

- **Base64url, not Base64**: JWTs use `-` and `_` instead of `+` and `/`, with padding stripped. Feeding a JWT part to a plain Base64 decoder often fails on exactly those characters.
- **An empty third part** (`header.payload.`) is an *unsecured JWT* (`"alg":"none"`). Some libraries mint these in test mode; production systems should reject them.
- **`aud` may be a string or an array** per the spec — the claims table renders both.
- Times are judged against **your machine's clock**. If your clock is wrong, the valid/expired verdict will be too.
