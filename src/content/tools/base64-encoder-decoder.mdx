## What it does

Convert text to Base64 and back with UTF-8 handled correctly, switch to the URL-safe alphabet used by JWTs and web tokens, or drop in a file (up to 5 MB) to get its Base64 string and a ready-to-paste `data:` URI. Decoding an image data URI shows the image itself.

## Examples

**Unicode round-trip.** The pre-filled sample — Czech diacritics plus an emoji — encodes to `QWhvaiEgRMOpasOgIHZ1IOKAlCDEjWXFoXRpbmEgaSBlbW9qaSDwn5qAIGZ1bmd1asOtLg` (URL-safe mode). Decode it back and every character survives, which is exactly what naive `btoa`-based tools get wrong.

**A small logo as a data URI.** Drop a 12 KB PNG on the file zone: you get the Base64, a `data:image/png;base64,…` URI ready for a CSS `url()` or an `<img src>`, and a preview confirming it's the right file.

**Reading a Basic auth header.** `Authorization: Basic dXNlcjpodW50ZXIy` — paste the token part in decode mode to see `user:hunter2`. (And that's why Basic auth without TLS is plaintext.)

## Edge cases & notes

- **Padding:** standard Base64 pads with `=` to a multiple of 4; the URL-safe variant conventionally drops it. The decoder accepts input with or without padding, and with whitespace/line breaks (common in email-wrapped content).
- **A length of 4n+1** can never be valid Base64 — the tool flags it as truncation instead of guessing.
- **Data URIs pasted whole** (`data:text/plain;base64,SGVsbG8`) are recognized in decode mode; only the payload after the comma is decoded.
- **The ~33% size rule:** every 3 bytes become 4 characters. A 5 MB file produces a ~6.7 MB string — fine for a clipboard, unpleasant inside a source file; prefer real assets over data URIs beyond a few KB.
